## 1. Product overview

### 1.1 Problem

Drivers, riders and fleet operators routinely choose between multiple routes that differ
in physical road quality, yet mainstream navigation systems optimise primarily for time,
distance and traffic. They do not surface road-hazard evidence such as potholes, cracks,
damaged patches, waterlogging, uneven or subsided surfaces, or speed bumps. As a result,
the "fastest" route may also be the riskiest for the vehicle, the rider or the cargo.
Existing hazard information, where it exists at all, is scattered, unauditable and rarely
tied to a specific route segment with transparent evidence.

### 1.2 Proposed solution

SafeRoute AI compares the routes a routing provider actually returns for a given
destination. For the road segments that require assessment, it obtains imagery **only
from permitted sources**, runs a documented OpenCV preprocessing and quality-check
pipeline, and applies an Ultralytics **YOLO11** road-hazard detector. A backend
**deterministic risk engine** converts verified detections into hazard-risk scores per
route using documented formulas. A **grounded LLM layer** explains the verified results
in natural language. The frontend presents the route alternatives, the supporting
evidence, the disclosed limitations, and a recommendation.

The product's defining principle is **evidence honesty**: every claim shown to a user
must trace back to verified backend data, and missing or insufficient evidence must be
disclosed as *unknown / unassessed* — never presented as evidence of a safe road.

### 1.3 Intended users

| User | Need |
|---|---|
| Everyday commuters | Choose a route that avoids poor road conditions. |
| Two-wheeler riders | Avoid potholes and uneven surfaces that cause loss of control. |
| Fleet / delivery operators | Reduce vehicle damage, downtime and cargo risk. |
| Emergency / service drivers | Prefer routes with fewer physical road hazards. |
| Municipal / planning analysts *(future)* | Understand hazard distribution along corridors. |

### 1.4 Primary use case

A user enters a destination and receives a comparison of the routes actually returned for
that trip. Each route shows its hazard-risk score, the hazard evidence behind it, an
explicit coverage/limitation statement, and a plain-language explanation. The user can
then make an informed choice.

### 1.5 Project scope

**In scope (intended):**
- Destination input and retrieval of genuinely available route alternatives.
- Segment-level assessment of hazards using YOLO11 on permitted imagery.
- Deterministic, documented, testable hazard-risk scoring.
- Grounded LLM explanation of verified backend results.
- Frontend presentation of alternatives, evidence, limitations and recommendation.

**Out of scope (unless separately approved):**
- Guaranteeing a fixed number of route alternatives (routes are shown only as returned).
- Real-time traffic optimisation or turn-by-turn navigation.
- Any imagery acquisition that is not from a permitted source.
- Mixing facility counts into the hazard score (see Rule 11).
- Any safety score or claim generated by the LLM.

### 1.6 Current reality (as of this PRD)

The workspace currently contains only `master_rules.md`. No dataset, model weights,
environment, source code, backend, frontend or integrations exist yet. This PRD therefore
describes requirements to be built and does not assert that they exist.

## 2. User journey

The required flow is below. Each step states what the system must do and the honesty
constraint that applies.

1. **User enters a destination.**
   The user supplies a destination (and optionally an origin or current location). The
   system validates the input and, if geocoding is required, resolves it through the
   selected routing provider. Nothing is assumed about the destination beyond what the
   provider returns.

2. **The system obtains available routes from a selected routing provider.**
   The system requests route alternatives from the chosen provider and uses **only the
   routes actually returned**. It must not synthesise, duplicate or pad routes to reach a
   count. When fewer than four valid alternatives are returned, it shows fewer than four
   (Rule 10).

3. **The system identifies road segments requiring safety assessment.**
   Routes are decomposed into assessable road segments. The system determines which
   segments can be assessed given imagery availability and which cannot, and marks the
   latter as **unassessed**.

4. **The system obtains imagery only from permitted sources.**
   Imagery is obtained solely from sources whose access and reuse are documented as
   permitted. The system must **never** assume that a routing API grants permission to
   download or reuse street-level imagery (Rule 8). If no permitted imagery is available
   for a segment, that segment is recorded as unassessed.

5. **OpenCV performs documented preprocessing and quality checks.**
   A single documented preprocessing pipeline (e.g., decoding, colour conversion,
   validation, dimension handling) is applied consistently, and only where justified and
   tested. The system rejects or flags corrupt, empty, unreadable or unsupported images
   rather than silently treating them as clean.

6. **YOLO11 detects supported road hazards.**
   The YOLO11 detector runs on preprocessed images and returns structured detections
   (hazard class, confidence, bounding box, image/segment identifiers). Only **supported
   and trained** classes are reported. Unsupported or untrained classes are reported as
   such, not fabricated (Rules 4, 5).

7. **The backend aggregates verified detections and calculates deterministic hazard-risk
   scores.**
   The deterministic risk engine converts verified detections into per-segment and
   per-route hazard-risk scores using documented formulas, configured hazard severities
   and image-coverage information. This engine — not the LLM — owns all safety
   calculations (Rule 7).

8. **The system compares available routes and presents a recommendation.**
   Routes are compared using their computed hazard-risk scores and disclosed coverage.
   The recommendation is derived from the deterministic results. If coverage is
   insufficient for a route, that limitation is shown alongside (or above) any score.

9. **The LLM explains the recommendation using verified backend results.**
   The LLM receives verified backend data and produces a natural-language explanation. It
   may parse user preferences and explain results. It must not invent routes, road
   conditions, hazards, facilities, measurements or safety claims, and must not override
   the deterministic engine (Rules 7, 12). A fallback explanation is provided if the LLM
   is unavailable.

10. **The frontend displays the route alternatives, evidence, limitations and
    recommendation.**
    The UI presents the returned routes, hazard evidence, coverage/limitation
    disclosures, the recommendation and its explanation. It clearly distinguishes
    working features, sample/simulated data, missing coverage and unvalidated
    capabilities (Rule 20).

**Cross-cutting honesty constraint for the journey:** At no point may the product imply
that unavailable imagery, unsupported hazard classes, unassessed segments, incomplete
route coverage, or unintegrated services are already available or verified. Every such
gap must be surfaced to the user as *unknown / unassessed / not available*, and never as
proof that a road is safe (Rules 9, 20).

## 3. Goals, non-goals and success criteria

### 3.1 Goals
- Provide an evidence-grounded comparison of genuinely available routes.
- Detect supported road hazards with a reproducible Ultralytics YOLO11 pipeline.
- Compute transparent, deterministic, testable hazard-risk scores.
- Explain results faithfully via an LLM without allowing it to fabricate evidence.
- Disclose missing coverage and limitations honestly.

### 3.2 Non-goals
- Replacing full turn-by-turn navigation.
- Guaranteeing route counts, imagery availability or hazard-class coverage.
- Providing legal, insurance or engineering-certified safety assessments.

### 3.3 Success criteria (measured only when actually run)
- Detector metrics (precision, recall, mAP) reported **only** from executed evaluation,
  never estimated or fabricated (Rule 14).
- Risk engine produces identical outputs for identical inputs (determinism) and handles
  missing/failed inputs explicitly.
- Every displayed claim traces to verified backend data; missing coverage is disclosed.
- Documented, reproducible commands exist for setup, preprocessing, inference, scoring
  and tests.

## 4. Functional requirements

### 4.1 Routing & destinations
- FR-R1: Accept a destination (and optional origin) and obtain route alternatives from the
  approved routing provider.
- FR-R2: Display only routes actually returned; never fabricate alternatives.
- FR-R3: Handle and surface provider errors, missing routes and zero-result cases.
- FR-R4: Decompose routes into assessable segments with stable identifiers.

### 4.2 Imagery
- FR-I1: Acquire imagery only from permitted sources (Rule 8).
- FR-I2: Record imagery provenance, timeliness/staleness, and failures.
- FR-I3: Treat missing/stale/inaccessible/insufficient imagery as unassessed (Rule 9).

### 4.3 Image processing (OpenCV)
- FR-C1: Provide a single documented preprocessing pipeline used for both training and
  inference.
- FR-C2: Validate images (corrupt, empty, unsupported, unreadable) and report failures.
- FR-C3: Preserve image dimensions where required; apply only justified transformations.
- FR-C4: Never modify original source images; write annotated outputs to safe paths.

### 4.4 Hazard detection (YOLO11)
- FR-D1: Use Ultralytics YOLO11 for detection.
- FR-D2: Gate training on dataset availability, annotation integrity, split integrity,
  environment compatibility and GPU availability (Rule 4).
- FR-D3: Return structured detections (model version, image/segment IDs, class,
  confidence, bounding box, status, errors).
- FR-D4: Report only supported/trained classes; disclose unsupported ones honestly.

### 4.5 Deterministic risk engine
- FR-K1: Compute hazard-risk scores from verified detections using documented formulas.
- FR-K2: Account for hazard severity, segment length, image coverage and failures.
- FR-K3: Distinguish detected hazards, no detections, insufficient coverage, failed
  acquisition and unassessed segments (Rule 9).
- FR-K4: Be deterministic and unit-testable; identical inputs → identical outputs.

### 4.6 Route comparison
- FR-X1: Compare routes using computed scores and disclosed coverage.
- FR-X2: Produce a recommendation grounded in deterministic results.
- FR-X3: Never present an unassessed route as safe.

### 4.7 Facilities (separate concern)
- FR-F1: Provide nearby facilities (e.g., hospitals, pharmacies, restaurants, hotels,
  petrol pumps, police stations) from a permitted provider, where available.
- FR-F2: Keep facilities separate from the hazard score unless an explicit, documented
  and approved requirements change defines a facility-aware policy (Rule 11).

### 4.8 LLM explanation
- FR-L1: Explain only verified backend results; parse user preferences where permitted.
- FR-L2: Never fabricate routes, conditions, hazards, facilities, measurements or scores.
- FR-L3: Validate responses and provide a fallback when the LLM is unavailable (Rule 12).

### 4.9 Frontend
- FR-U1: Support destination input, route alternatives, hazard evidence, risk scores,
  facility information (kept separate), explanations, loading states and errors.
- FR-U2: Display coverage/limitation disclosures prominently (Rule 9, Rule 20).
- FR-U3: Avoid unnecessary frameworks; do not duplicate existing components (Rule 18).

## 5. Data & model requirements

- **Dataset:** Not yet present. Training requires a workspace-local dataset with verified
  licences, annotation format, class IDs, image–label pairing and no train/val/test
  leakage (Rule 15).
- **Hazard classes (target):** `pothole`, `crack`, `damaged_patch`, `waterlogging`,
  `uneven_surface`, `speed_bump`, `other`. Only classes actually present and trained may
  be reported (Rule 5).
- **Model version label:** `safroute-yolo11-v1` (architecture/size to be confirmed only
  after hardware and dataset checks and explicit approval).
- **Model selection:** Use validation results; keep the test set isolated until final
  evaluation. Training completion does not imply production readiness.

## 6. Non-functional requirements

- **Determinism:** Risk scoring reproducible for identical inputs.
- **Auditability:** Documented formulas, configuration, dataset provenance, model
  versions and commands (Rule 17).
- **Security:** No secrets in source; credentials via local environment configuration
  with documented safe setup (Rule 13).
- **Honesty:** Separate measured results from estimates and plans; never fabricate
  metrics (Rule 14, Rule 20).
- **Isolation:** All artifacts remain inside `D:\New folder (3)` (Rule 1).
- **Maintainability:** Minimal dependencies; inspect before editing; preserve existing
  work (Rule 18).

## 7. Constraints, assumptions and dependencies

**Constraints**
- Workspace isolation; one approved phase at a time (Rules 1, 3).
- No unauthorized downloads, installs, paid API calls, credential creation, dataset
  modification or training (Rule 19).
- Imagery and routing access are subject to third-party terms that must be verified.

**Assumptions (to validate)**
- A suitable routing provider and permitted imagery source will be approved.
- A workspace-local dataset and a CUDA-compatible PyTorch environment can be provided.
- Available hardware is adequate for the chosen YOLO11 size and schedule.

**Dependencies**
- Ultralytics YOLO11, OpenCV, a routing provider, a facilities provider (optional), an LLM,
  and a Python environment — **none yet installed or integrated**.
